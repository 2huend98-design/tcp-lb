# tcp-lb - 四层TCP负载均衡代理（C++20，个人学习项目）

- 在学习计算机网络时发现对 TCP 原理和 epoll 缺乏深刻理解，所以写了一个四层负载均衡代理。使用 reactor 模式，每连接由 ProxySession 管理，下挂两个 TcpConnection 分别对接客户端和服务端，每个 TcpConnection 用 readv / writev 与环形缓冲区交互；主要由事件驱动，事件不会来的情况才交给计时器。
- 代理没有上零拷贝这类优化，一开始的简单版本性能实在不够看，后来用环形缓冲区、减少用户态拷贝等方法，把性能提到至少能和 nginx / haproxy 放在一张表里比，对这个项目来说，是一个可以接受的程度。

## 快速开始

```bash
# 构建
mkdir build && cd build && cmake .. && make -j$(nproc) && cd ..

# 后台运行echo后端和代理
./build/bin/echo_server 9000 &
./build/bin/echo_server 9001 &
./build/bin/echo_server 9002 &
./build/bin/echo_server 9003 &
./build/bin/tcp_proxy config.conf &

# 用 tcpbench 当客户端，测传输速率
./build/bin/tcpbench 8080 --conns 16 --size_mb 64 --rounds 3

# 也可以用 nc 手动测试，本项目自带 echo 后端，收到数据原样发回
nc 127.0.0.1 8080
```

## 架构

```text
┌───── 一次转发的数据通路：ProxySession 两侧同住一个 worker EPOLL 循环 ──────────┐
│                                                                              │
│             client_conn                        backend_conn                  │
│                                                                              │
│  client ==> fd_c --readv--> [发送缓冲] --writev--> fd_b ==> echo:9000..9003   │
│        （读的一侧把字节 readv 进对方的发送缓冲，由对方 writev 发出）            │
│  client <-- fd_c <--writev-- [发送缓冲] <--readv-- fd_b <-- echo:9000..9003   │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

- 主 reactor 上 acceptor 只做接入，新连接按原子计数轮询分发到 4 个 worker；数据从进到出只有 readv / writev 两次拷贝，中间没有 memcpy。
- 两条 TcpConnection 互为 peer，readv 进环形缓冲、writev 出环形缓冲，双向透传。
- 一侧关闭走半关闭语义，缓冲排空后事件级联清理，全程不轮询。
- 唯一的时间机制是期限 timerfd（后端建连 3s / 每条 TcpConnection 传输停滞 300s）：
- 有些合法状态无法区分是连接挂起还是正在等待，这种情况交给定时器处理。
- 代码按模块分层：reactor/（事件循环）acceptor/（接入与分发连接）proxy/（连接与转发）balancer/（负载均衡）health/（后端健康）common/ config/。

## 和 HAProxy / nginx 对比

- 参照物：HAProxy 3.0.8（大缓冲档用 `MAX_BUF_SIZE=16M` 重编译）、nginx stream 1.24.0，均关闭零拷贝——与本项目同为用户态拷贝口径。4 个 echo 后端，4 个工作线程；参照组（hap / nginx）同为 4 线程。
- 环境：Ubuntu 24.04.5.1，9800X3D（8C16T）/ 48GB DDR5-6000，MTU 1500，内核 TCP 缓冲全线 autotune（手工设定会带来 RTO 过高的问题，`TCP_RCVBUF_BYTES` / `TCP_SNDBUF_BYTES` 仅作实验开关）。
- 方法：6 种缓冲 × 6 档并发，三方跑同一个矩阵；每格 2 轮预热 + 30 轮计量取中位数，每轮 8GB；停滞计时器 `TCP_IDLE_DEADLINE_SEC=60`（代码默认 300s）。

## 踩过的坑

- **RTO 退避冻结**：小缓冲 + 1024 高并发使连接经常处于暂停状态，在途数据被丢弃，多次重传失败后 RTO 变得很高，连接停滞几十秒。修法：适当放宽停滞计时器的时间（60s），给重传一定余地，并把内核缓冲区改回 autotune，减少长时间暂停的发生概率。
- **UAF**：关闭连接流程在关闭回调执行中导致对象析构，触发 UAF。修法：把关闭动作投递成任务异步执行，避免栈上析构仍在使用的对象。
- **string buffer erase 过慢**：output buffer 用 string 实现，消费数据后触发 O(n) 的 erase，严重占用 CPU 拉低吞吐。修法：改用环形缓冲区，生产消费均 O(1)。

## 已知边界

- 只在 loopback 上测过，真实网络路径没有数据。
- 单 reactor accept，连接建立速率的上限没专门测过。
